## Major：需要修改代码的阻断项

### M1 作者说明未经可见性分类进入玩家正文和下一次请求

位置：`world-runtime/src/model.mjs:20-30`（仅 schedule 有特殊过滤，其他 scene.narrative 保留）；`server.mjs` actions/revise 分支；`public/app.js:57` 事件说明输入；`knowledge.mjs:12-16,36-38` 摘录/导出复用场景原文。

正常作者流程可以在“人物私有”事实的事件说明中解释该事实。事实字段会被裁剪，但作者说明仍成为玩家场景正文、下一次 `compileContext` 历史和知识页。没有场景 audience/可见性元数据，也没有将作者审计说明和玩家叙事分开的提交字段。切换到玩家视图不能消除这条路径。不能靠过滤秘密字符串实现语义可靠修复。

关联：U-07/U-08、B-17、I-07/I-20、T-15/T-22。

最小修复：作者审计文本默认作者可见；显式单独发布玩家可见叙事/观察，场景可见性随不可变提交保存并由一个统一 ActorView 决定；公共状态不能从审计文本反向推断。更新兼容策略，旧无 audience 的作者场景保守处理。对玩家 UI、请求、搜索、章节、知识包、原文导出全部加正常工作流测试。

同一边界的补充：玩家 `world.card.description` 从原卡拷贝，未与裁剪后的主角 description 同步；作者将主角色描述标为 private 后，原卡描述仍是 UI 描述/卡片展示数据。应区分可读原件（作者导入管理）和玩家呈现字段，不让两个来源互相抵消隐私设置。

### M2 已终止关系在模型当前状态与知识导出中变回未标状态的关系

位置：`model.mjs` compactState 的 relations 投影；`knowledge.mjs` relations.md 与人物关系页。

独立普通流程验证：add_relation → end_relation。权威快照含 `status: ended, validUntil: 0`；模型“本轮公开状态”只收到 from/to/type/detail，知识关系页亦无 ended/有效期。UI 虽显示“已终止”，模型得到的当前关系和导出却仍像有效关系，历史含糊文字不能弥补结构化状态丢失。该投影还遗漏 relation.id，模型被提示使用 update_relation(id)/end_relation(id)，却没有获得这些 ID。

关联：U-08、I-15、T-14/T-20/T-22；长期正确性。

最小修复：当前关系过滤 ended，另给有界历史关系（标状态/时间），或完整传 id/status/validFrom/validUntil，并明确当前/历史语义。知识页同样显示状态、有效期与来源。测试终止、重建同类型关系、历史分支、模型可引用 ID。

### M3 锁定后的过期日程阻断推进，而不是按无效日程处理

位置：`store.mjs` advance 验证 scheduled operations 的 catch；`domain-state.mjs` LOCKED_FIELD。

普通流程验证：安排 NPC 稍后移动 → 作者锁定 NPC → advance。调用抛 `LOCKED_FIELD`，待办仍 pending。advance 只把 LOCKED_FACT 等旧错误当作前提失效；新实体/关系/变量锁采用 LOCKED_FIELD，被漏接。自主轮询捕捉后停整个自主模式，其他到期事项不能继续。这与“锁定不被覆盖”无冲突，但恢复/日程失效语义未闭环。

关联：I-11/I-16、T-18/T-19。

最小修复：统一可预期领域拒绝分类，锁定导致的失效写成可追溯 cancelled/blocked 日程，并确保其他允许事件照常处理；不可吞掉真实数据库/程序故障。补三类锁与多个到期事件测试。

## 完整目标的主要未关闭门（不等于都必须在无设备环境盲目实现）

### G3 U-10/U-14 / T-20～23：长篇、自然度和成本证据仍有限

## Minor / 工程改进

1. **CI 未覆盖新增核心。** `.github/workflows` 没有 world-runtime/test、test:world 或安装新运行时步骤；现有 launcher/sqlite 工作流只能覆盖上游。最少增加 Node24.19+ Linux 的锁定运行时安装、world 单测、HTTP/DOM；浏览器及桌面 matrix 独立标明。首次远程 CI 通过不代表新增核心有被运行。
2. **上游发行入口仍可误导。** README 已醒目标识旧 install/launcher 不属于 fork，Pages/manifest 改 workflow_dispatch 是正确的。可是 docs/index.html、product.html、package.repository、install.* 仍指向 flizzywine，手动发 Pages 也会发布这些上游下载。保留来源链接合理；在所有可执行安装入口增加明确归属提示，站点发布前重定向到 fork 说明，而非粗暴改成不存在的本 fork Release。
3. **知识导出原文不是惰性文本保证。** references.md、events.md、chapters.md 直接拼接原始正文（clean 只去 CR），而其他字段 escape。下载 JSON 本身不会执行内容，当前 UI 也 textContent，因此这里不是已验证的浏览器执行问题；但将 files 写成 Markdown 交给支持 HTML/远程图片的阅读器，原文会被当标记解释。应统一选择转义/引用原文或随包明确“未净化来源内容，阅读器需禁用 HTML/远程加载”；不要宣称知识包所有文本已做安全 Markdown 编码。
4. **可维护性。** 多个业务模块一行包含整段事务/HTTP分支/UI流程（app.js 95行、server.mjs115行）；低行数没有降低复杂度。格式化、提取具名处理函数/投影函数并保留测试能明显改善审查。CONTRACTS 的主体仍旧字段清单，后来能力只分散补充；应统一版本化 API/操作合同。
5. **资料私有 UI 文案有限。** set_reference 下“私有”固定 holderId=player，含义是玩家+作者、对NPC私有，不是作者独享；文案已写该含义，但缺作者独享资料选项，容易与事实私有机制混淆。
