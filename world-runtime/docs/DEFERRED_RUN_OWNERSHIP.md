## Cancellation outcome visibility

The ordinary functional review of2a9d6ad requested one error-reporting correction: a failed cancellation save could skip notification and disappear during cleanup. cancelQueuedRun now treats cancellation and persistence as separate outcomes. It sets cancelled, attempts the local save, records a generic RUN_PERSISTENCE warning with the storage code on rejection, and still invokes the terminal notifier. Its return value explicitly says persisted:false rather than claiming a durable cancellation. Notification callback rejection remains an observable Promise rejection.

The server keeps an unpersisted cancellation in its existing live run entry, overlays its diagnostic in the current run view, includes it in reconnect/cancel responses, and collects it in close warnings before resources are disposed. Cleanup removes ordinary settled runs but does not hide these unresolved records. The UI displays the cancellation persistence warning. There is no second canonical state store or claim that volatile diagnostics survive process loss; startup still reconciles the durable record it actually finds. A draft with an unresolved cancellation warning is not advertised as ready to retry settlement.

Evidence is limited to ordinary function-level storage substitutes proving save rejection still notifies, preserves/returns the warning before queue ownership ends, and exposes notification rejection.
